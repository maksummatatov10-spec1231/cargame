МОИ ОШИБКИ НА ПРОЕКТЕ GODOT 4.3 — ЗАПИСКА СЕБЕ В НОВЫЙ ЧАТ
==========================================================

Это не общий гайд по Godot. Это список конкретных ошибок, которые я реально
совершил на проекте cargame за 29 релизов, с причинами и с тем, как их ловить.
Многие я совершал по несколько раз подряд — эти отмечены отдельно, они самые
опасные.

Порядок: сначала то, что ломало работу больше всего.

Обновлено после v3.8. Два свежих провала — оба в моём собственном служебном
коде, оба уронили проект целиком у пользователя:
- := от Variant → все скрипты не компилируются (часть 3.2);
- случайные UID в .import → 88 ошибок в логе (часть 2.9-бис).

И два новых фиктивных теста (таблица в 1.1) — оба повторяли ошибки, уже
записанные в этом же файле. Читать этот файл перед работой, а не только
дописывать в него.

Обновлено после v3.9. Пользователь прислал скриншот: машина розовая. Плюс те
же 44 ошибки UID, что и до исправления.
- цвет: Vector4 вместо Color обходит конверсию sRGB (часть 2.9-кватер);
- ALPHA в шейдере отключил тени у всего кузова (2.9-квинт);
- 64 одинаковых Shader.new() на машину (2.9-секст);
- queue_free() + call_deferred() → material is null (2.9-септ);
- UID уже были верные — врал кеш .godot (в конце 2.9-бис). Об этом надо было
  написать в описании релиза;
- 4 предупреждения GDScript, которые я счёл косметикой, указывали на мёртвый
  код (часть 3.3).

ЧАСТЬ 2. ОШИБКИ В GODOT 4.3 — ДВИЖОК
====================================

Всё проверено по исходникам 4.3. Номера строк — из 4.3-stable.

2.1. $Node не падает громко — он кладёт null
--------------------------------------------

    @onready var _fps : Label = $Fps      # узла нет -> _fps == null
    ...
    _fps.text = "60"                       # ошибка КАЖДЫЙ кадр

Дало две ошибки в логе: Node not found один раз и Invalid assignment of
property 'text' ... on a base object of type 'null instance' — постоянно.

Как правильно: get_node_or_null + создание виджета, если его нет. Ещё лучше —
строить UI кодом целиком. Узел, созданный тем же кодом, что его использует, не
может потеряться.

2.2. Vector3.slerp может вернуть ненормализованную ось
------------------------------------------------------

core/math/vector3.h:238:

    Vector3 axis = cross(p_to);
    real_t axis_length_sq = axis.length_squared();
    if (axis_length_sq == 0.0f) { return lerp(...); }   // только ТОЧНЫЙ ноль
    axis /= Math::sqrt(axis_length_sq);

Возведение в квадрат вдвое сокращает диапазон экспоненты. Если векторы почти
совпадают, |cross|² попадает в денормальную область float32 — не ноль,
проверка пропускает, значащих бит нет.

Замерено: при |cross| = 1e-21 длина «нормированной» оси 0.999673.
Basis::set_axis_angle требует единичной — ассерт срабатывает.

Это дало 7900 ошибок за сеанс: два почти одинаковых вектора — это
установившееся состояние фильтра нижних частот, 4 колеса × 120 Гц.

Как правильно: для близких векторов — lerp + normalized() с проверкой длины.
Разница с точным slerp при 5° — 2.5e-4 градуса.

Quaternion.slerp безопасен — там есть явная ветка для близких значений.

Тот же класс ошибки: A.cross(B).normalized() без проверки длины. Защита if up
!= Vector3.UP не работает — это точное сравнение float.

2.3. SpringArm3D ставит камеру в физике, а скрипт затирал это каждый кадр
-------------------------------------------------------------------------

scene/3d/physics/spring_arm_3d.cpp — process_spring() вызывается только из
NOTIFICATION_INTERNAL_PHYSICS_PROCESS и ставит ребёнка через
set_global_transform().

А у меня последней строкой _process было:

    camera.transform = Transform3D.IDENTITY

Это сажает камеру в начало координат руки — на pivot, 1.55 м над машиной. И
поскольку это последняя запись перед кадром, она побеждала пружину всегда. На
экране — вид отвесно вниз на крышу.

Правило: трансформом ребёнка SpringArm3D владеет рука. Скрипт задаёт только
spring_length, arm.position/rotation и camera.fov.

2.4. Курс машины нельзя брать из basis.get_euler().y
----------------------------------------------------

Разложение Эйлера в порядке YXZ подмешивает тангаж и крен в рыскание.

тангаж/крен   ошибка курса
------------------------------------------------------------------------------
10°/10°       1.75°
30°/20°       11.2°
60°/40°       48.1°

Камеру уводило с оси машины на каждой кочке.

Как правильно: брать вектор «вперёд» и проецировать на землю:
    var forward := -xform.basis.z
    var flat := Vector2(forward.x, forward.z)
    return atan2(-flat.x, -flat.y)

Ошибка 0.000°.

2.5. rate * delta — сглаживание, зависящее от частоты кадров
------------------------------------------------------------

В _physics_process delta постоянна, в _process — нет. Перенёс камеру и получил
разное поведение на разных fps: 84.8% при 30 fps против 76.4% при 240.

Как правильно: 1.0 - exp(-rate * delta). Одинаково при любом fps.

2.6. Однополюсный фильтр молча превращается в пустышку
------------------------------------------------------

blend = TAU * hz * dt, потом clamp(0..1). При 120 Гц всё выше 19 Гц даёт
больше 1.0 и обрезается — фильтра нет вообще.

Я поставил 30 Гц и был уверен, что фильтрую. Пришлось ставить 8 Гц.

Правило: посчитай коэффициент численно и проверь, что он < 0.95.

2.7. max_physics_steps_per_frame — порог зависания
--------------------------------------------------

main.cpp:4031. При отставании движок доигрывает до N полных тиков в кадре,
кадр удлиняется, и всё насыщается ровно на physics_hz / N.

- 120 Гц / 8 = 15.0 fps ← пользователь получил именно это
- 120 Гц / 3 = 40 fps

Ловушка: одно число управляет двумя противоположными вещами. Ниже порога время
идёт медленнее; на пороге игра залипает. Зависание хуже — при 39 fps ехать
можно, при 15 нет.

2.8. Настройки FPS: половина имён — из Godot 3
----------------------------------------------

- debug/settings/fps/force_fps — имя из Godot 3, в 4.3 его нет вообще (грепнул
  всё дерево — ноль совпадений). Строка мёртвая.
- Реальное имя: application/run/max_fps (main.cpp:2377).
- display/window/vsync/vsync_mode=1 — это VSYNC_ENABLED, и оно перебивает
  любой max_fps, ограничивая частотой монитора.

2.9. importer_defaults вызывали те сообщения, которые я ими глушил
------------------------------------------------------------------

resource_importer_texture.cpp:110-131 печатает «текстура используется как
карта нормалей» ровно когда compress/normal_map == 0. А мой блок
[importer_defaults] выставлял 0 всем текстурам.

Поставить 1 глобально нельзя — красно-зелёное сжатие выбрасывает синий канал,
это испортит цветовые карты.

Как правильно: поштучный .import на каждую текстуру.
editor_file_system.cpp:2435-2459: свой .import имеет приоритет, а
importer_defaults подмешиваются, только если своего нет.

И роль надо брать из glTF, а не из имени файла: RIM_OS.png и
Fanali_Anteriori_OS.png — карты нормалей, несмотря на суффикс _OS.

2.9-бис. UID: я сам сгенерировал 44 нерабочих идентификатора
------------------------------------------------------------

Вторая по стоимости ошибка. Лог пользователя (v3.7):

    core/io/resource_uid.cpp:132 - Condition "!unique_ids.has(p_id)" is true.
        Returning: String()          ← 44 раза
    Can't find file 'uid://chxql2rtxgf8b'.   ← 44 раза

Мой tools/make_import_files.py писал UID как uuid.uuid4().hex[:13]. Две
независимые ошибки в одной строке.

Ошибка 1 — не тот алфавит. core/io/resource_uid.cpp:38-41:

    // These constants are off by 1, causing the 'z' and '9' characters
    // never to be used. This cannot be fixed without breaking
    // compatibility; see GH-83843.
    static constexpr uint32_t char_count = ('z' - 'a');        // 25, не 26
    static constexpr uint32_t base = char_count + ('9' - '0');  // 34, не 36

Алфавит — это a..y плюс 0..8. Символы z и 9 движок не выдаёт и не принимает
обратно. А uuid4().hex — это шестнадцатеричная строка, где 9 встречается
постоянно: 9 попала в 29 из 44 файлов. text_to_id() превращал такую строку в
число, которое id_to_text() уже не мог записать так же → поиск в кеше
промахивался у каждой текстуры.

Именно поэтому имена в ошибках (chxql2rtxgf8b) не совпадали ни с одной строкой
в моих файлах: движок печатал каноническое написание.

Ошибка 2 — случайность. Каждый запуск скрипта менял все UID и заставлял
переимпортировать весь проект.

Как правильно: выводить UID из пути детерминированно и кодировать той же
функцией, что и движок (id_to_text), — тогда round-trip верен по построению:

    digest = hashlib.sha256(("res://" + rel_path).encode()).digest()
    value = int.from_bytes(digest[:8], "big") & 0x7FFFFFFFFFFFFFFF

Проверка, которая это ловит (check_uids в project_check.py): text -> id ->
text должно вернуть исходную строку. Плюс проверка на уникальность и на
отсутствие z/9.

Отдельный урок: если в логе идентификаторы, которых нет ни в одном файле
проекта — не ищи их grep-ом бесконечно. Значит, движок печатает
нормализованную форму, и сравнивать надо после нормализации. Я потерял время,
гоняя grep по репозиторию.

Продолжение в v3.9: ошибки вернулись после исправления. Пользователь поставил
v3.8 и увидел те же самые 44 Can't find file. Проверил численно: все 44
идентификатора из нового лога — это канонические формы UID из v3.7, ни один не
совпадает с v3.8.

Значит, файлы уже правильные, а старые значения приходят из кеша редактора:
.godot/uid_cache.bin и .godot/editor/filesystem_cache*.
editor_file_system.cpp:337 читает UID из строки кеша (fc.uid =
split[2].to_int()), а project_settings.cpp:487 загружает uid_cache.bin при
старте. Пути в кеше указывают на записи, которых больше нет.

Правило: после изменения UID или .import папку .godot надо удалить. Иначе
редактор продолжает верить кешу. Это надо писать в описании релиза, а не
считать, что пользователь догадается. Я не написал — и получил «исправленный»
баг второй раз.

2.9-тер. path.s3tc — путь, которого может не быть
-------------------------------------------------

В шаблоне .import я жёстко прописал только один вариант:

    path.s3tc="res://.godot/imported/<файл>-<md5>.s3tc.ctex"

resource_importer_texture.cpp:656-680 пишет вариант s3tc только если
should_import_s3tc_bptc(), а при high_quality — вообще bptc. Ветка выбирается
по OS::has_feature, которая для s3tc/bptc уходит в Utilities::has_os_feature
(utilities.cpp:259-283) и спрашивает у драйвера, поддержан ли формат.

То есть я зафиксировал результат проверки железа в текстовом файле. Правильно
— не выдумывать path.* руками: движок перезапишет .import сам при первом
импорте. Мои .import нужны только ради [params].

2.9-кватер. Розовая машина: два разных промаха с sRGB
-----------------------------------------------------

Пользователь прислал скриншот: кузов BMW розовый вместо тёмно-красного. Мой
шейдер вмятин подменяет материалы, и терял цвет дважды.

Промах 1 — забыл : source_color у uniform.

    uniform vec4 albedo_colour = vec4(...);            // было
    uniform vec4 albedo_colour : source_color = ...;   // стало

Промах 2 — важнее и незаметнее. Я передавал компоненты:

    mat.set_shader_parameter("albedo_colour",
        Vector4(albedo.r, albedo.g, albedo.b, albedo.a))   # НЕВЕРНО
    mat.set_shader_parameter("albedo_colour", albedo)      # верно

variant_converters.h:209-214 конвертирует sRGB → линейный только для
Variant::COLOR:

    } else if (type == Variant::COLOR) {
        Color c = p_variant;
        if (p_linear_color) {
            c = c.srgb_to_linear();
        }

Vector4 уходит в ветку «просто скопировать». То есть даже с правильным
source_color конверсии бы не было.

Численно: (0.81, 0.25, 0.27) → (0.91, 0.53, 0.56) — ровно розовый.

Правило: цвет в шейдер — всегда Color, uniform — всегда source_color.
Компоненты передавать нельзя.

2.9-квинт. Запись ALPHA отключает тени у всего объекта
------------------------------------------------------

Мой шейдер писал ALPHA = base.a; безусловно, чтобы поддержать стёкла. Побочный
эффект — весь кузов перестал отбрасывать тень.

scene_shader_forward_clustered.cpp:416:

    bool has_base_alpha = (uses_alpha && (!uses_alpha_clip || ...)) || ...;
    bool has_alpha = has_base_alpha || uses_blend_alpha;
    return !has_alpha || (uses_depth_prepass_alpha && ...);

uses_alpha выставляется самим фактом присваивания ALPHA в коде (:113,
usage_flag_pointers["ALPHA"]), а не значением. Даже ALPHA = 1.0 убивает тень.

Как правильно: два варианта шейдера. Непрозрачный вообще не упоминает ALPHA.
Прозрачный пишет и осознанно теряет тень — стеклу она и не нужна.

2.9-секст. Shader.new() на каждую поверхность
---------------------------------------------

_make_dent_material() вызывался на поверхность, и внутри был Shader.new() — 64
одинаковых шейдера только на BMW, и заново на каждый респавн и каждое нажатие
V.

Shader — это ресурс, а не состояние объекта: параметры живут в ShaderMaterial.

3.2. := не работает с Variant — уронил весь проект в v3.7
---------------------------------------------------------

Это самая дорогая ошибка по последствиям: одна строка не дала загрузиться всем
скриптам сразу.

    res://scripts/damage.gd:496 - Parse Error: Cannot infer the type of
        "is_wheel" variable because the value doesn't have a set type.
    res://scripts/vehicle.gd:-1 - Compile Error:
    res://scripts/game_settings.gd:-1 - Compile Error:
    res://scripts/hud.gd:-1 - Compile Error:

Виноватый код:

    for part in hits:                  # hits — Dictionary → part это Variant
        var is_wheel := part in [      # `in` от Variant → тоже Variant
            DamageModel.Part.WHEEL_LF, ...]

Здесь два источника Variant, и оба надо знать:

1. Переменная цикла по Dictionary — всегда Variant. Ключи словаря не
   типизированы, статического типа взяться неоткуда.
2. in возвращает Variant, если хоть один операнд — Variant.
   gdscript_analyzer.cpp:2956:

       } else if (left_type.is_variant() || right_type.is_variant()) {
           // Cannot infer type because one operand can be anything.
           result.kind = GDScriptParser::DataType::VARIANT;

Дальше срабатывает gdscript_analyzer.cpp:1929 — тот самый текст ошибки.

Так же ведёт себя индексация словаря: var x := dict[key] — тоже Variant, даже
если ключ типизирован.

Решения:
- типизировать массив (Array[Vehicle]);
- писать тип явно (var p: Vector3 = ...);
- обернуть в конвертор (int(key), float(dict[k]), String(...));
- вместо x in [...] — типизированная функция static func is_wheel(part: int)
  -> bool. У неё тип есть по определению.

Почему это не поймали: gdparse проверяет синтаксис, gdlint — стиль, мой
typecheck.py — сигнатуры вызовов. Ни один не моделирует типы. Все три сказали
«чисто» на коде, который движок не грузит. Пришлось написать
tools/variant_check.py.

Урок про -1 в логе: vehicle.gd:-1 - Compile Error: с пустым текстом и строкой
-1 означает не ошибку в этом файле. Это каскад: файл не скомпилировался,
потому что не собралась его зависимость. Искать надо единственную строку с
настоящим номером и текстом — она была в самом начале лога. Я едва не начал
чинить vehicle.gd.

ЧАСТЬ 4. ФИЗИКА МАШИНЫ — ЧТО БЫЛО НЕВЕРНО
=========================================

4.1. Забыл инерцию трансмиссии — машину трясло
----------------------------------------------

В первой передаче двигатель отражает 0.24 × 12.9² ≈ 40 кг·м² против
собственных 1.2 у колеса. Без учёта этого колесо разгонялось на 18 рад/с за
один тик, шина отвечала огромной силой, колесо швыряло обратно.

4.2. Все три машины были настроены на занос
-------------------------------------------

Градиент недостаточной поворачиваемости K = Wf/Cf − Wr/Cr:

           было                                        стало
------------------------------------------------------------------------------
BMW        −0.408 °/g, критическая скорость 217 км/ч   +1.37
Defender   −0.258                                      +2.17
пикап      −0.251                                      +2.66

Отрицательный K — это неустойчивость, а не «характер»: выше критической
скорости любое возмущение нарастает само.

4.3. Нормаль контакта — по треугольнику, скачок 31.8° за тик
------------------------------------------------------------

HeightMapShape3D — сетка треугольников, луч возвращает нормаль одного
треугольника. На границе ячейки она меняется мгновенно.

Замерено: скачок до 31.8° за тик, что под весом машины даёт 7.7 кН вбок — 5.2
м/с² на ровной с виду земле.

Решение: интерполированная нормаль от террейна + фильтр.

4.4. Знак вращения колёс
------------------------

Godot правосторонний, машина смотрит в −Z. Положительный поворот вокруг +X
уводит верх колеса назад. Проверка: (0, 0.33, 0) при +0.3 рад даёт z = +0.098.

4.5. Застревание было не про сцепление
--------------------------------------

Первая передача даёт 1.08 g, самый крутой склон карты — уклон 0.85. Машина
садилась днищем: гребень поднимается на 1.00 м на базе 2.63 м.

Правило: прежде чем «добавить мощности» — проверь, касаются ли колёса земли
вообще.

4.6. Ассеты: ничего нельзя принимать на веру
--------------------------------------------

- Ни в одном файле не было анимации → ветер только шейдером.
- Цвета материалов в FBX от 3ds Max почти все чёрные — цвет задавала шейдерная
  сеть, не пережившая экспорт. Классифицировать надо по именам материалов, а
  где имена бессмысленные (Material #1958) — по геометрии.
- FBX 7400 требует 32-битных заголовков узлов; из-за непроброшенной версии в
  рекурсию все такие файлы выглядели пустыми.
- Масштаб и ориентацию надо выводить из реальных размеров (колёсная база), а
  не из заголовка файла.

7.4. Как писать проверки, чтобы они не были фикцией
---------------------------------------------------

Это мой главный системный провал — 9 раз. Правила:

- Сломай нарочно. Написал проверку — внеси баг, убедись, что она падает, верни
  код. Не сделал этого — считай, что проверки нет.
- Ломай тремя способами, а не одним. Проверка UID ловила «плохой символ», но
  пропускала дубликат. Проверка Variant ловила in, но пропускала dict[key].
  Спроси: «какие ещё формы у этого бага?»
- Вырезай комментарии и докстроки перед поиском подстроки. Дважды напоролся:
  докстрока, объясняющая баг, содержит слова из бага.
- Проверяй, что тест что-то нашёл. Ноль совпадений — это провал, а не успех.
  Пиши assert found >= N.
- Смотри на весь проект, а не на один файл. Баг с Variant шёл через границу
  файлов и потому был невидим однофайловой проверке.
- Тестируй фичу только если симулятор умеет её моделировать. Иначе тест
  зелёный по построению.
- Проверяй на распакованном ZIP, а не в рабочей копии: в архив легко забыть
  положить файл.

7.5. К своим инструментам относись строже, чем к игровому коду

Оба самых дорогих бага (v3.7, v3.8) были не в игре, а в моём служебном коде:
генератор .import и мои же проверки. Причина простая: игру тестирует
пользователь, а инструменты — никто, кроме меня.

Практически:
- Генератор чего-либо должен быть детерминированным. Прогони дважды и сравни
  md5sum — второй запуск обязан быть no-op.
- Если генерируешь формат движка (UID, .import, .tscn) — транскрибируй функцию

- Не записывай в файлы результат проверки железа (как я с path.s3tc). Движок
  сам решит это на машине пользователя.

7.6. GDScript: что писать по умолчанию
--------------------------------------

- Типизируй всё. Array[Vehicle], а не Array. Это ловит ошибки на парсере, а не
  у пользователя.
- := — только когда тип очевиден. Из Dictionary/нетипизированного Array он не
  работает. Пиши var x: float = dict[k] или float(dict[k]).
- x in [...] в присваивании — запрещено. Делай static func ... -> bool.
- Никогда $Node — только get_node_or_null с проверкой. Ещё лучше — строй UI
  кодом.
- Имена переменных сверяй со списком членов Node/CanvasItem/Node3D и 127
  глобальных функций (tools/godot_api.json), а не по памяти.
- Файл < 1000 строк. Превысил — выделяй модуль (так родился
  vehicle_recovery.gd).

7.7. Физика и математика
------------------------

- Считай числом, а не на глаз. Каждый раз, когда я оценивал «примерно», я
  ошибался в разы.
- Сглаживание — только 1 - exp(-rate * dt), никогда rate * dt.
- Проверяй, что фильтр вообще фильтрует: коэффициент должен быть < 0.95, иначе
  clamp превращает его в пустышку.
- Курс — из forward-оси, не из get_euler().
- Осторожно со slerp для близких векторов — бери lerp + проверку длины.
  Quaternion.slerp безопасен, Vector3.slerp нет.
- Знак устойчивости важнее «характера»: отрицательный градиент недостаточной
  поворачиваемости — это неустойчивость, а не стиль.

7.8. Как общаться с пользователем
---------------------------------

- Только по-русски.
- Не объявляй баг исправленным без доказательства. Три релиза подряд
  «починенного» заднего хода стоили доверия: «у меня руки опускаются».
- Честно говори, что не проверено. Godot в песочнице не запускается, значит
  «вмятины отрисовываются» — это гипотеза, а не факт. Так и пиши.
- Свои ошибки называй своими, без обтекаемых формулировок.
- Не предлагай то, от чего уже отказались (чистка репозитория, звук —
  пользователь их отклонил).
- Проси конкретные числа, если они нужны: fps со счётчика я так и не получил,
  потому что недостаточно настойчиво просил.

7.9. Гигиена репозитория
------------------------

- Ветка фиксирована — работай и пушь только в неё.
- Никогда git checkout <файл> для отката временной правки: так потерялись
  изменения в project.godot. Копируй в /tmp и возвращай cp.
- Каждый релиз: ZIP только проекта Godot, коммит в release/, тег, GitHub
  Release с описанием на русском.
- Загрузка ассета в Release может падать (uploads.github.com рвёт соединение)
  — тогда ZIP всё равно лежит в release/ в репозитории, и надо честно об этом
  сказать.

Главное в одной фразе
---------------------

Почти все мои крупные провалы — не от незнания Godot, а от того, что я верил
себе без проверки: верил, что тест работает; что причина найдена; что оценка
верна; что правка ничего не задела.

Движок почти всегда честно говорит правду в исходниках. Надо просто пойти и
прочитать.

И вторая фраза, добытая в v3.7-3.8: самые дорогие мои баги были не в игровой
логике, а в служебном коде, который я написал сам — генератор .import-файлов и
мои же проверки. Игровой код пользователь тестирует, а инструменты не
тестирует никто, кроме меня. Значит, к ним нужна та же строгость: сломать
нарочно, проверить на всём проекте, не верить подстроке.
